# Рабочие проекты: локальные папки и GitHub

## Назначение

Рабочий проект — обычный проект приложения с дополнительным полем workspace.
Он объединяет диалоги, проектную память, локальную рабочую папку, отдельный RAG,
Git/MCP и файловые инструменты. Это контекст для всех задач, а не режим /help.
Единственный генеративный провайдер остаётся DeepSeek API.

## Подключение и переключение

Нажмите «＋ Проект», выберите публичный GitHub или локальную папку, укажите URL
вида https://github.com/owner/repository либо полный путь к папке. Название
можно указать отдельно. Приложение создаст проект и пустой диалог, скопирует
документацию и запустит локальную индексацию. Ход виден в «Управлении RAG».
Дождитесь завершения, затем задавайте вопросы обычным сообщением или через /help.

«Рабочий проект» переключает на последний чат выбранного проекта; если чатов
нет — создаёт новый. «＋ Диалог» создаёт отдельную задачу в текущем проекте.
Открытие старого чата возвращает его рабочий проект. Чаты, summary, facts,
память задачи и проектная память не переносятся при переключении. Пользовательские
предпочтения остаются общими для профиля. Историю с сообщениями нельзя переносить
или копировать между разными рабочими репозиториями: создайте новый диалог.

Сам ассистент — встроенный проект по умолчанию. Старые проекты, содержащие только
память, продолжают поддерживаться и используют корень ассистента для инструментов.

## GitHub и локальные папки

GitHub импортируется неглубоким git clone в data/workspaces/repositories/<id>.
Код не запускается, зависимости проекта не устанавливаются, skills из репозитория
не активируются. Git не запрашивает пароль и не использует сохранённые credentials.
Поддерживаются публичные HTTPS-ссылки на корень репозитория без токенов и query.
Приватные репозитории и URL отдельной ветки/файла не поддерживаются.

Ветка и коммит относятся к локальной копии. Это не проверка свежести GitHub:
автоматического fetch/pull/push нет. Изменения локальной папки после обновления
документации попадут в индекс; кнопка индексации не скачивает новые коммиты.

При подключении локальной папки она не копируется и её исходники не меняются.
Проект без Git поддерживается: ветка недоступна, список файлов строится по папке.

## RAG и источники

Для внешнего проекта индексируются корневые Markdown и README, docs/doc/
documentation/api/schemas, openapi/swagger и основные манифесты (package.json,
pyproject.toml, Cargo.toml, go.mod, requirements.txt, pom.xml). Поддерживаются
MD, MDX, RST, TXT, HTML, JSON, YAML, TOML, XML; текстовые спецификации копируются
с дополнительным суффиксом .txt. Символические ссылки, скрытые файлы и зависимости
не индексируются. Пределы: 600 файлов, 1 МиБ на файл, 12 МиБ суммарно.
Это индекс документации и манифестов, а не полная индексация исходного кода.
Если документации нет, индекс сообщает ошибку и нужно добавить README/docs.
Обычный чат и /help при этом остаются доступны: они явно сообщают об отсутствии
RAG и могут использовать Git/список файлов, чтобы начать новую задачу.

Для собственных исходников сохранён корпус README/docs без исторических отчётов и docs/archive.
Состав актуальных руководств перечислен в docs/README.md.
Каждый внешний проект имеет data/workspaces/<project_id>/documents,
rag_index.sqlite3 и rag_evaluations.json. Модель эмбеддингов/реранкер общие,
но документы, векторы и результаты сравнений отдельные. Поиск проверяет права
доступа профиля. Найденные фрагменты передаются DeepSeek только при вопросе.

В обычном чате подключённого рабочего проекта RAG включается автоматически
(baseline/structural). /help использует тот же индекс и актуальный Project MCP.
Project MCP в обычном чате вызывается моделью по необходимости. Контекст и аудит
ответа содержат project_id, имя и корень рабочей папки.

## Файловые инструменты и дальнейшие задания

Git MCP и Filesystem MCP привязаны к выбранной рабочей папке. Инструменты
запускаются из установленного ассистента, пакеты в чужом проекте не требуются.
Общий выключатель останавливает серверы всех загруженных проектов.
Сейчас модель умеет явно запрошенный экспорт в reports выбранного репозитория
(у самого ассистента — workspace/reports). Произвольное редактирование кода
не добавлялось: это отдельные сценарии дня 34 поверх уже правильного корня.
Новые задания планировщика также привязываются к выбранному проекту.

## API и хранение

POST /api/projects: {name, create_dialog: true, workspace: {kind: github|local,
source: URL|абсолютный путь}}. Возвращает project и conversation; индексация фоновая.
POST /api/workspace/select: {project_id: id|null}. Выбор хранится отдельно для
профиля в data/workspace_selection.json. null выбирает самого ассистента.
GET /api/state возвращает active_workspace_project_id и проекты с workspace.
RAG и Filesystem lifecycle принимают workspace_project_id в query; доступ
проверяется сервером. Запросы конкретного диалога всегда используют project_id
самого диалога, независимо от глобального выбора и query-параметров.

Тесты test_workspaces.py проверяют раздельные базы, память и обычный чат,
права профилей, переключение корней, экспорт в нужный проект, валидность URL,
извлечение документации и настоящий Project MCP для другой папки.
