# Машина задач, handoff и артефакты

## Независимые механизмы

task_state управляет этапами и допустимыми действиями. task_memory хранит цель
и решения текущего чата; она независима от машины задач. История full/summary/
sliding/facts — ещё один отдельный механизм. Отключение машины задач не удаляет
её данные и не запрещает обычный чат или память задачи.

Общий выключатель машины задач сохраняется в data/task_control.json.
Локальная активность задачи — active/paused; её этап сохраняется при паузе.
/state и /task-state возвращают отчёт локально. Пауза блокирует дальнейшую
генерацию, включая /help, когда машина задач включена.

## Этапы и события

| Исходный этап | Событие | Новый этап |
| --- | --- | --- |
| planning | approve_plan | execution |
| execution | complete_execution | validation |
| execution | return_to_planning | planning |
| validation | pass_validation | done |
| validation | validation_failed | execution |

Начальное состояние — planning, active, manual. У задачи есть описание,
план, current_step, expected_action, required_artifacts и transition_history.
Переход выполняется сервером по разрешённому событию, а не произвольной заменой
stage в тексте ответа. UI показывает доступные переходы. Режим automatic допускает
автопродолжение со стороны браузера; остановка автопилота/ручной режим запрещают
запросы automatic. Это не серверный сервис, который продолжает чат после закрытия
браузера. Для отложенной работы предназначены отдельные расписания.

## Контроллер и инварианты

Перед генерацией модель получает допустимые типы действий текущего этапа.
После генерации отдельный запрос проверяет черновик, нарушения инвариантов,
stage_complete, recommended_event и требуемые артефакты. Инварианты собираются
из слоёв пользователя, проекта и задачи (invariants.py); активны только включённые
правила. Ошибка разбора проверки не является разрешением выполнить действие.

Контроллер — LLM-проверка в приложении, а не доказательство корректности кода
или замена файловым ограничениям. Файловые пути, разрешения MCP и доступ к
проекту проверяются отдельно обычным кодом. Операции schedule_management и
file_export допускаются политикой на разных этапах; сам доступ к инструменту
всё равно требует разрешения и подходящего запроса.

## Handoff и история этапа

При переходе сохраняется передача контекста: цель, решения, ограничения,
результаты и дальнейшая работа. task_handoffs содержит происхождение и usage,
active_handoff_ids выбирает применяемые передачи. stage_run_id различает
повторные прохождения этапа. Когда машина задач включена, история/summary/facts
для генерации ограничиваются текущим прохождением этапа, а handoff передаёт
сведения предыдущего. При отключении используются обычные обмены активной ветки.

## Артефакты

Артефакт — сохранённый файловый результат ответа, а не обещание модели в тексте.
artifacts.py извлекает файловые блоки, проверяет относительные пути и сохраняет
байты в data/artifacts/<conversation_id>/<artifact_id>/<filename>.
Для логического path ведутся версии: новая становится active, старая сохраняется
с superseded_by. Запись содержит sha256, size_bytes, mime_type, source_message_id
и stage_run_id. Лимит одного артефакта — 2 МиБ.

Для переходов с обязательными результатами проверяются существование файлов,
целостность и статус валидации. Просто перечислить требуемое имя в ответе
недостаточно. Скачать/просмотреть результат можно через HTTP-маршруты артефактов.
Импорт/копирование артефактов имеет собственную обработку в app.py; JSON-экспорт
диалога не следует считать полным бэкапом всего окружения.

Filesystem MCP-экспорт — другой путь: новый Markdown-отчёт создаётся в reports
рабочего проекта, с безопасным уникальным именем. Он не является универсальным
редактором исходников. При заблокированном черновике созданные в этом проходе
отчёты удаляются, созданные расписания откатываются. Это локальные компенсирующие
действия, не общая транзакция между всеми хранилищами.

Источники реализации: task_state.py, task_handoff.py, task_policy.py, invariants.py,
artifacts.py; оркестрация и ограничения переходов — app.py.
