# День 32 — автоматическое ревью PR

## Что реализовано

`code_review.py` запускает того же DeepSeekProvider из `agent.py` без Flask,
чата, пользовательской памяти и MCP. Не меняет код, ветки, диалоги и пресеты.
Получает две Git-ссылки, вычисляет merge-base и читает diff и файлы из
зафиксированного head. Несохранённые и незакоммиченные изменения не входят в ревью.
Переименования представлены удалением и добавлением; удалённый код остаётся в diff.

Отдельный RAG для ревью использует локальный BM25: разбивает код и документацию
на фрагменты по 60 строк с перекрытием 12, ищет по именам файлов и тексту diff,
выбирает до пяти фрагментов документации и пяти фрагментов кода. Это лексический
поиск с генерацией ответа по найденному контексту; эмбеддинги и загрузка моделей
не требуются. Индекс чата, `/help` и `rag_documents` не изменяются. Корпус строится
заново в памяти для конкретного head; история чата не используется.

DeepSeek получает diff, список файлов, найденные фрагменты и ограничения.
Отвечает JSON; программа проверяет формат, категории, приоритеты и принадлежность
строк замечаний добавленным/удалённым строкам diff. Такая проверка отсеивает
несуществующие адреса, но не доказывает правильность анализа модели.
Незавершённый ответ, неверный JSON или адрес отменяют весь отчёт и публикацию.

Результаты: `review.md`, `review.json`, `audit.json` в отдельной выходной папке.
Аудит содержит SHA base/head, список изменённых и исключённых файлов,
найденные источники с диапазонами строк и оценками, хеш запроса, статус,
фактический usage провайдера. Полный запрос, ключ и reasoning не сохраняются.
В отчёте три раздела: потенциальные баги, архитектурные замечания, рекомендации.
При пустом списке явно сообщается, что замечания не сформированы.

## Границы контекста

Читаются только Git blobs текстовых исходников `.py`, `.js`, `.ts`, `.html`,
`.css`, `.md`, `.toml`, `.yml`, `.yaml` и `requirements.txt`. Символические ссылки
не включаются в RAG. Включены workflow в `.github`, другие скрытые пути исключены.
Исключены `data`, `.env`, зависимости, модели, инструменты, журналы, отчёты,
учебные fixtures и архив документации, а также имена с secret/credential/private_key.
Фильтрация имён не заменяет проверку случайно закоммиченных секретов в обычном коде.

Лимиты: diff 180000 байт, один источник 200000 байт, корпус 12000000 байт,
запрос 260000 символов, ответ до 6000 токенов. Слишком большой diff/запрос
отклоняется до API; большие/бинарные источники пропускаются с аудитом.
Изменённые файлы получают приоритет в корпусе. Код PR и его тесты не исполняются.

## Локальный запуск

Сначала закоммитьте проверяемые изменения в отдельном локальном репозитории
или ветке. Push не нужен. Укажите настоящие ссылки вместо примеров:

```powershell
.\.venv\Scripts\python.exe code_review.py --base main --head HEAD --dry-run
.\.venv\Scripts\python.exe code_review.py --base main --head HEAD
```

Первый запуск только собирает контекст и аудит, без сети и текста ревью.
Второй отправляет diff и RAG в DeepSeek API и может расходовать средства;
ключ загружается из локального `.env`. На GitHub Actions `.env` не загружается.
Скрипт сам ничего не публикует и не выполняет Git push.

Без изменения текущего рабочего дерева можно подготовить учебный diff:

```powershell
.\.venv\Scripts\python.exe scripts/day32_demo.py
.\.venv\Scripts\python.exe scripts/day32_demo.py --live
```

Скрипт создаёт временный локальный Git-репозиторий с двумя известными
регрессиями: деление на ноль при пустом наборе и потеря locked facts.
Контракты находятся в отдельном документе, чтобы проверить использование RAG.
Первый запуск без API; `--live` выполняет настоящий запрос DeepSeek.
Отчёты остаются в `reports/day32_demo_dry` или `reports/day32_demo_live`.
Это учебный модуль, а не тест действующих `context_manager.py` или `storage.py`.

## Подключение GitHub после выбора правильного репозитория

В текущем checkout подключён другой удалённый проект. Ничего не публикуется,
remote не меняется, runner не устанавливается и не регистрируется автоматически.
Workflow `.github/workflows/ai-review.yml` подготовлен, по умолчанию выключен.

После отдельного согласования правильного репозитория:

1. Перенести согласованную версию проекта и workflow в основную ветку правильного
   репозитория. Код ревью должен уже присутствовать в base до первого учебного PR.
2. Зарегистрировать отдельный Windows x64 self-hosted runner с дополнительной
   меткой `deepseek-review`. Использовать отдельную учётную запись/машину с
   ограниченным доступом; не подключать к посторонним репозиториям.
3. Подготовить доверенное Python-окружение **вне runner checkout**, установить
   зависимости проекта. Workflow не устанавливает зависимости из PR.
   Указать полный путь к его `python.exe` в Repository variable `AI_REVIEW_PYTHON`.
4. Добавить ключ в Repository secret `DEEPSEEK_API_KEY`. В Actions ключ не хранится
   в `.env` или исходниках. Это отдельное хранилище секретов GitHub.
5. Задать Repository variables `AI_REVIEW_REPOSITORY=владелец/правильный-репозиторий`
   и `AI_REVIEW_ENABLED=true`. Без обоих значений задание пропускается.
6. Запустить runner, открыть обычный PR из ветки этого же репозитория от владельца
   личного репозитория. Draft и PR из fork не запускают задание. Конфигурация
   рассчитана на личный репозиторий; для организации правила допуска нужно пересмотреть.

Используется `pull_request_target` (opened/synchronize/reopened/ready_for_review),
чтобы workflow исполнялся из доверенной default branch, а не из изменяемого PR.
GitHub всегда берёт сам workflow из основной ветки репозитория, даже если
base PR указывает на другую ветку. Поэтому исправление `permissions` в отдельной
ветке не начинает действовать до его принятия в default branch. См.
[правило GitHub](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#pull_request_target).
Checkout выполняется только для base SHA. Head загружается как Git-объекты,
не checkout и не import; ref проверяется на соответствие SHA события.
Нельзя добавлять в этот workflow checkout, запуск скриптов или установку
зависимостей из PR. Причина и ограничения self-hosted runners описаны в
[официальном руководстве GitHub](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target).
Доступные ключу права — чтение содержимого и запись issues/pull-requests.
Для комментариев к PR явно задано `pull-requests: write`: в первом реальном
запуске одного `issues: write` оказалось недостаточно (HTTP 403). Исправление
нужно отдельно принять в основную ветку и проверить повторным запуском.
Запись содержимого репозитория токену не разрешена.
Другие workflow того же репозитория также требуют контроля доступа к runner.

После успешного ответа Action создаёт один комментарий от `github-actions[bot]`
с маркером `deepseek-agent-review`, при следующем запуске обновляет его.
Перед публикацией сверяет актуальный head PR; устаревший результат пропускается.
Отчёт и аудит также сохраняются как Actions artifact на 14 дней; файлы кода,
полный diff и ключ туда не добавляются. Замечания могут цитировать фрагменты кода.
Имя artifact включает номер попытки, поэтому повторный запуск сохраняет отдельный отчёт.
Сам комментарий не исправляет код и не выполняет merge.

## Что требуется для сдачи

Локальные unit-тесты с fake-provider подтверждают сбор diff, поиск, фильтрацию
и обработку ответа. Live-demo отдельно подтверждает фактическую работу DeepSeek
на учебном diff. Ни один из них не подтверждает запуск GitHub Actions на PR.

Для завершения дня 32 нужен реальный PR в правильном репозитории, успешный
запуск на локальном runner, комментарий с найденными известными ошибками
и повторный запуск после исправления. Пока публикация запрещена, этот этап
остаётся невыполненным. Нельзя называть день полностью сданным по локальному demo.

выходных токенов (1104 всего). Отчёт сохранён локально в
`reports/day32_demo_live/review.md`, аудит — рядом. Это не запуск на реальном PR.

Отчёт сохранён как artifact. Публикация комментария пока не прошла: HTTP 403
